# Concept Basis — Sorting & Custom Comparators

> [!abstract] Minimal spanning set for **imposing an order, and exploiting one you have imposed**. One entry per **new idea you have to learn**. Two halves that are usually taught apart and belong together: the *algorithms and their guarantees*, and the *comparator* — which is where almost every real bug and almost every interview follow-up lives. Cross-listed entries (↗) are developed further elsewhere but belong here too.

## Why this file is not "here are five sorting algorithms"

> [!warning] **Nobody will ask you to implement quicksort. They will ask you to sort by two keys in opposite directions, and then ask why your comparator throws.**
>
> The algorithms matter for exactly three questions — *is it stable*, *is it in-place*, *what is the worst case* — and those three answers are what decide which library call you make. Everything past that is either a comparator problem or a **reason to sort at all**, and the second is the genuinely transferable half: sorting is almost never the answer, it is the *preprocessing* that makes the answer possible, and T3 is about what it buys you.

## Mechanism axes

| Axis | Values |
|---|---|
| **What you actually sort** | the elements · **derived keys** · **indices** (a permutation) · **events derived from the elements** · the *queries* rather than the data |
| **Where the order comes from** | one field · several fields · a derived quantity · a **global pairwise relation** (no field to read) · an **externally supplied alphabet** · **pairwise constraints with no key at all** |
| **What the sort must guarantee** | nothing · **stability** · in-place · a worst-case bound · **only the k-th element** |
| **What the domain allows** | arbitrary comparables · **bounded integer range** · fixed-width digits · **nearly sorted / run-rich** |
| **Why you are sorting** | adjacency · monotonicity · a **safe greedy order** · grouping · an **event sweep** · to answer offline |
| **What happens after the sort** | a single scan · two pointers · binary search · **an insertion process that shifts what is already placed** |
| **Cost model** | comparisons cheap · **comparisons expensive** (minimise their *number*) · **key computation expensive** (decorate) · moves expensive (sort indices) · **data does not fit in memory** |
| **What breaks** | an **invalid comparator** — non-transitive, no equality case, subtraction overflow · sorting destroys the indices you needed · sorting destroys a required input order · **no total order exists** |

## T1 · The algorithms and their guarantees

Four facts, not five implementations. You need these to *choose*, and to answer the follow-up.

| # | Problem | Source | The new idea |
|---|---|---|---|
| 1 | What your library actually runs, and the `Ω(n log n)` floor | *concept — the question behind "why not just sort?"* | **Comparison sorting cannot beat `n log n`, and the proof is one sentence: a comparison tree with `n!` leaves has depth at least `log₂(n!) ≈ n log n`.** That bound is what makes T5 and the `O(n)` sorts interesting — they beat it only by *not comparing*. Then the three facts that actually decide your call: **stability** (equal elements keep their input order), **in-place**, and **worst case**. Real libraries pick differently and you should know which you have: Python and Java-on-objects use **Timsort** — stable, `O(n)` extra space, and it detects existing runs so nearly-sorted input is near-linear; C++ `std::sort` uses **introsort** — quicksort that falls back to heapsort at depth `2 log n`, so `O(n log n)` worst case but **not stable** (`stable_sort` is a different call); Java-on-primitives uses **dual-pivot quicksort** — not stable, which is invisible for `int` and is why the two Java sorts differ. The only trap worth memorising: **`std::sort` is not stable and Python's is**, so code that quietly relies on tie order is portable in one direction only. |
| 3 | Counting sort, and the prefix step that makes it a sort | *classic — the `O(n)` sort behind radix and bucket* | **Tally each value, then prefix-sum the tallies, and each count becomes a *starting position*.** The tally alone tells you how many of each value there are, which is enough to *rewrite* the array — but not enough to place arbitrary records, and the prefix step is exactly what converts "how many are smaller" into "where does this one go". `O(n + V)`, so it is a win precisely when the value range `V` is comparable to `n` and a disaster when values are `10⁹`. New because it is the first sort that **does not compare anything**, which is how it escapes #1's bound, and because that same prefix-over-the-value-axis is a technique in its own right ([[Prefix Sums & Difference Arrays]] #13). Written stably — walk the input backwards, decrementing positions — it becomes the building block for #4. |
| 4 | Radix sort, and stability as a load-bearing property | *classic — the reason stability is not a footnote* | **Sort by the least significant digit, then the next, and so on — and the whole thing works *only* because each pass is stable.** Stability is what preserves the previous digits' ordering while you reorder by the current one, so `d` stable passes of #3 produce a full sort in `O(d · (n + b))`. New and generalisable well past digits: **any multi-key sort can be done as successive stable single-key passes, from the least significant key to the most significant** — which is a real alternative to writing the multi-key comparator of #6, and sometimes the only option when the keys arrive one at a time or when the comparator would be awkward. The reflex to keep: *if someone asks why stability matters, this is the answer* — not tie-breaking politeness, but composability. |

## T2 · Writing a comparator that is valid

> [!danger] **This family is where the marks are.** Every entry here is a bug you can write in one line and will not notice until the input is large enough, or a language throws at you.

| # | Problem | Source | The new idea |
|---|---|---|---|
| 5 | The strict-weak-ordering contract, and the four ways to break it | *concept — Java's `IllegalArgumentException: Comparison method violates its general contract!`* | **A comparator must define a *consistent total preorder*, and if it does not, the sort is entitled to do anything — including crash, loop, or silently drop elements.** The contract: **irreflexive** (`cmp(a, a)` is false / returns 0), **antisymmetric**, and **transitive**, *including transitivity of equality*. The four ways people break it, in order of how often: (a) **no equality case** — `return a.x > b.x ? 1 : -1` never returns 0, so equal elements report both `a < b` and `b < a`; Timsort detects this and throws, `std::sort` reads out of bounds and is undefined behaviour. (b) **subtraction overflow** — `return a - b` is correct for small ints and wrong the moment `a - b` overflows, which is why `Integer.compare(a, b)` exists. (c) **a comparator over a *partial* order**, like "a is better than b if a beats b in every dimension" — genuinely non-transitive-friendly and simply not sortable; you want #14's reasoning. (d) **a mutable key** — sorting by a field that something else changes during the sort. New because the failure mode is *not* a wrong answer: it is a crash or corruption far from the mistake, and knowing to say "let me check this is a strict weak ordering" out loud is the entire content. |
| 6 | Multi-key ordering, including keys in opposite directions | LC **937** *(Reorder Data in Log Files)* · LC **2545** | **Compare on the first key; only when it ties do you look at the second — and the two keys may run in opposite directions.** The idiom is a chain (`cmp(a.k1, b.k1)` then `cmp(b.k2, a.k2)` — note the swap, which *is* the descending direction), and the two things to get right are that **negating a comparator is not the same as reversing the whole sort** when there are several keys, and that **"leave ties in input order" is not a key at all — it is stability**, so you write fewer comparisons and pick a stable sort. New because it is where descending-on-one-key-ascending-on-another appears, which is the shape of most real "sort by X then Y" requests and is what #19 depends on. The clean way to write it in every language: a tuple key `(k1, -k2)` where negation is available, or an explicit chained comparator where it is not. |
| 7 | Largest Number | LC **179** | **The comparator encodes the objective, and reads no field at all: `a` comes before `b` iff `a+b > b+a` as strings.** There is no key you can extract from a single number that produces the right global order — sorting by value, by first digit, or by length all fail (`9` before `34`, but `30` before `3`), because "which order of *this pair* makes a bigger concatenation" is a statement about the pair. So you make the pairwise question itself the comparator. New, and the most important entry in T2, because it inverts the usual direction: normally you find the key and sort by it, here **you define the comparison directly from the thing you are optimising**. It comes with a **proof obligation** — you must argue the relation is transitive, or #5 applies — and the argument is that `a+b > b+a` is equivalent to comparing `a/(10^{|a|}−1)` against `b/(10^{|b|}−1)`, which *is* a key, so a valid total order exists. Same move: LC **1029** (sort by the *difference* between two costs, not by either cost) and every "sort by which of two orderings is locally better" greedy. |
| 8 | Custom Sort String · Verifying an Alien Dictionary | LC **791** · **953** | **The order is supplied from outside as a permutation of the alphabet, so you invert it into a rank table and compare ranks.** Build `rank[ch] = position in the given order` once, then every comparison is an `O(1)` lookup — and characters absent from the given order need an explicit policy (usually rank `−1` or "keep at the end"), which is the part people forget. New because the ordering is **data, not code**: it arrives at runtime and cannot be baked into a comparator, which is the same shape as sorting by a caller-supplied priority list, a locale, or a configured preference order. Cheap and very commonly asked in the "here is a weird ordering, sort by it" form. |
| 9 | Sort Integers by The Number of 1 Bits | LC **1356** | **Decorate, sort, undecorate — compute the key once per element instead of once per comparison, and keep the original index if you need it.** A comparator that recomputes `popcount` is called `O(n log n)` times for `n` distinct keys; building `(key, index, value)` tuples first costs `n` key evaluations and then sorts on a cheap field. Two payoffs, and the second is the one people miss: **the index rides along**, so sorting no longer destroys "where did this come from" — which is what makes "return the *indices* of the two numbers that sum to the target" survive a sort, and what an **argsort** (sorting a permutation of indices, leaving the data untouched) does in general. New because it separates *the order you want* from *the array you have*: sort a key array, sort an index array, or sort the data — three different answers to "the input must not be reordered", "moves are expensive", and "the key is expensive". |
| 10 | Compare Version Numbers | LC **165** | **Lexicographic order on a *representation* is not the order on the value it represents.** `"1.10"` sorts before `"1.9"` as a string and after it as a version, because string comparison sees `'1' < '9'` at the third character and never learns that the field is numeric. So you **split into components and compare them component-wise, numerically**, with a policy for unequal lengths (missing components are zero, so `1.0` equals `1`). New because the bug is invisible in small tests and universal in real systems — the same class of error orders `"file10"` before `"file9"`, sorts `"10/01/2026"` before `"09/12/2026"` unless the format is `YYYY-MM-DD`, and is why zero-padding and ISO dates exist. The reflex: **when the thing you are sorting is a string that means something, ask whether the string's order agrees with the meaning's order.** |

## T3 · What sorting actually buys

> [!tip] Sorting is rarely the answer; it is the step that makes the answer cheap. Each entry here is a *different reason* to pay `n log n`, and being able to say which one you are buying is what separates "I sorted it" from a designed solution.

| # | Problem | Source | The new idea |
|---|---|---|---|
| 11 | Minimum Absolute Difference | LC **1200** · *and LC **220**'s offline cousin* | **After sorting, everything that needs comparing is *adjacent*, so an `O(n²)` pairwise question becomes one linear scan.** The closest pair of values must be neighbours in sorted order — if `a < c < b` then `c` is closer to both, so a non-adjacent pair can never be the minimum. That exchange argument is the entry, not the code. New because it is the cheapest and most reusable of sorting's dividends: it also collapses duplicate detection, "are any two within `t`", grouping equal values, and "the `k` closest to `x`" into linear scans. The general statement to hold: **sorting converts a global question about all pairs into a local question about neighbours, whenever the quantity you care about is monotone in the distance between them.** |
| 12 | 3Sum | LC **15** | **Sorting creates monotonicity, which is what two pointers and binary search need in order to exist at all.** Fix one element, and the remaining two-sum over a sorted range is solved by converging pointers in `O(n)` — because moving left up strictly increases the sum and moving right down strictly decreases it, so each step *discards* a whole range without checking it. Total `O(n²)` instead of `O(n³)`. New as a reframe rather than a technique: the sort is not part of the answer, it is what **manufactures the discard argument** the answer depends on ([[Two Pointers]] #1). The corollary is the useful half — *if a solution needs to skip a range, ask whether sorting would justify the skip* — and the same purchase makes binary search available, which is why so many "does a valid X exist" problems begin with an unremarked `sort()`. Sorting also hands you the free deduplication that 3Sum's distinct-triplet requirement needs. |
| 13 | Non-overlapping Intervals · Minimum Arrows to Burst Balloons | LC **435** · **452** | **Sorting establishes a *safe greedy order*, and which key you sort by is the entire problem.** Sort intervals by **end** and greedily keep every one that starts after the last kept end: the exchange argument is that among all intervals compatible so far, taking the one that finishes earliest never rules out anything the alternatives would have allowed. Sort the same data by **start** and the greedy is simply wrong. New because it is the entry that makes the *choice* of key visible as a decision requiring proof — by start, by end, by length, by ratio, by difference are all natural and at most one is correct — and because the proof obligation *is* the interview answer. Companion instances worth recognising as the same move: sort by deadline for scheduling, by ratio for fractional knapsack, by the *difference* of two costs for LC 1029. The general rule: **the correct key is the one your exchange argument needs, so find the argument first and let it name the key.** |
| 14 | Meeting Rooms II | LC **253** | **Sort *derived events*, not the elements — each item becomes a `+1` at its start and a `−1` at its end, and the two lists are then swept in order.** The maximum number of concurrent meetings is the running sum's peak, which no ordering of the *intervals* gives you directly. New because it changes **what the sortable unit is**: you manufacture `2n` timestamps out of `n` objects and sort those, which is the entry point to every sweep-line problem — skyline, rectangle union, "how many are active at time `t`", and the whole of interval counting. The tie rule is where this is won or lost: **an end at the same instant as a start must be processed first** if touching intervals do not conflict, and that is a decision about the problem, not about the sort. The heap formulation is [[Heap]] #14 and the difference-array formulation is [[Prefix Sums & Difference Arrays]] #18 — worth knowing all three, because they are the same sweep with different bookkeeping. |
| 19 | Queue Reconstruction by Height | LC **406** | **Choose the sort order so that later placements cannot invalidate earlier ones.** Each person knows how many *taller* people stand ahead of them, so sort by height descending with count ascending (#6's opposite directions) and insert each person at index `k` — correct because everyone already placed is taller, so a later insertion shifts only people who do not count the newcomer, leaving every earlier answer intact. New, and distinct from #13, because of **what happens after the sort**: #13 sorts to make a *scan* safe, and here the sort exists to make a **mutating insertion process** safe, which is a stronger requirement — the arrangement itself keeps changing and the ordering must guarantee that the changes are harmless. Once you have that idea, "process in an order where each step's effect is invisible to the steps already done" is a whole family: reconstructing from partial-rank information, applying operations whose effects would otherwise interfere, and rebuilding a sequence from "how many bigger things are before me". |

## T4 · When no key exists

| # | Problem | Source | The new idea |
|---|---|---|---|
| 15 | Course Schedule II | LC **210** | **When the order is given by *pairwise constraints* rather than by a key, no comparator can exist and sorting is the wrong tool.** A comparator must answer for *every* pair, and a constraint list only tells you about some pairs, so the relation is a **partial order** — you cannot compare two unrelated items, and forcing a comparator to invent an answer breaks #5's transitivity. The right structure is a graph and the right algorithm is a **topological sort**, which also gives you the thing a comparator never could: *detecting that no valid order exists at all* (a cycle). New as a **recognition skill** rather than an algorithm — the giveaway phrasing is "must come before", "depends on", "is a prerequisite of" — and it is worth holding here rather than only in [[Graphs]] #6, because the moment you reach for `sort()` on this is the moment you have misread the problem. |
| 16 | Couples Holding Hands · Minimum Swaps to Sort | LC **765** · *classic* | **The minimum number of swaps to sort a permutation is `n − (number of cycles)`, and you find the cycles by following where each element must go.** Treat the array as a permutation `i → target(i)`; it decomposes uniquely into disjoint cycles, and a cycle of length `L` needs exactly `L − 1` swaps, so the total is forced — there is nothing to optimise. New because it replaces a search with a **structural count**: "what is the fewest swaps" sounds like it needs a greedy or a BFS, and the answer is a property of the permutation you can read off in one pass. Once you see the cycle decomposition you also get "is this reachable by an even number of swaps" (parity), which is what decides the 15-puzzle. Note the boundary: this is the count for **arbitrary** swaps; restrict to *adjacent* swaps and the answer becomes the inversion count instead ([[Sorted Containers & Order Statistics]] #2), which is a different quantity for the same-looking question. |

## T5 · When you cannot sort normally

| # | Problem | Source | The new idea |
|---|---|---|---|
| 17 | Sort a nearly-sorted array | *classic — "each element is at most `k` from its final position"* | **Bounded displacement means you never need more than `k+1` elements in view: a min-heap of size `k+1` emits the next correct element every time you push.** `O(n log k)`, and it is the honest answer to "the data is almost in order" — as is knowing that **Timsort already exploits this for free**, detecting ascending and descending runs and merging them, so nearly-sorted input is close to `O(n)` in Python and Java without you doing anything. New because it is the *input-shape* axis: sortedness is not binary, and "almost sorted" is a resource you can spend. Worth pairing with the negative version — a single element moved very far ruins the `k` bound while barely affecting Timsort. Heap machinery is [[Heap]] #24. |
| 18 | External merge sort | *concept — "sort 100 GB with 8 GB of RAM"* | **Sort what fits, write the sorted runs to disk, then `k`-way merge them — because merging is sequential and sequential I/O is the only kind you can afford.** Pass one produces `⌈N/M⌉ sorted runs; pass two merges them with a heap of size `k`, reading a block from each run at a time. The design content is the *reason*: random access to disk is catastrophic and merge sort is the one comparison sort whose access pattern is purely sequential, which is why this and not quicksort. New because it introduces a cost model where **comparisons are free and I/O is not**, and that model is what makes the same algorithm look different — you tune `k` against buffer memory, and one more pass costs another full read-write of the data. The `k`-way merge itself is [[Heap]] #7. Included as a systems-flavoured question that does get asked at SDE-2 and above; the same reasoning is behind MapReduce's shuffle and every database's sort-merge join. |
| 20 | Find the second largest with the fewest comparisons | *classic — the tournament argument* | **When you are minimising the *number of comparisons* rather than time, the answer is a tournament: `n − 1` comparisons find the maximum, and the second largest is among the `⌈log₂ n⌉` elements the maximum beat — total `n + ⌈log₂ n⌉ − 2`.** The naive two-pass scan uses `2n − 3` and is asymptotically identical, which is exactly why this is a different question: **`O(n)` is not the metric here, the constant is.** New because it introduces the axis at all — comparisons as the scarce resource, which is what matters when each comparison is a network call, a user asking a person to judge two options, or a physical measurement — and because the argument, that only elements defeated by the winner can be second, is the reusable half. Worth knowing the shape of the lower-bound results too (finding max *and* min needs `⌈3n/2⌉ − 2`, by comparing elements in pairs first), since "can you do it in fewer comparisons" is a standard tightening once you have given an `O(n)` answer. |

## Self-audit

**Borderline calls, and which way I went**

- **The whole file versus splitting "sorting algorithms" from "comparators".** Nearly split them. Kept together because the interview never separates them — you are asked to sort by something awkward, and the follow-up is about stability or about beating `n log n`, and both halves are needed in the same breath. T1 is deliberately four entries rather than one per algorithm to keep the balance right.
- **Quickselect was drafted native and demoted to ↗.** I argued it belonged here because the content is the *recurrence*, not the pointer mechanics — then checked [[Two Pointers]] #17 and found the geometric-series argument, the randomised pivot and the `O(n²)` worst case already written there. The draft entry was a near-duplicate. Recorded rather than quietly deleted, because it is the second instance of the same 4C-i failure in two sessions; see below.
- **#3 and #4 kept separate.** Both are non-comparison sorts and radix is literally repeated counting sort. Split because #4's idea is *stability composes into a multi-key sort*, which is a general statement about ordering and is the answer to "why does stability matter" — and it would be invisible if buried inside counting sort.
- **#11, #12, #13 and #14 are all "sort first, then something cheap".** The most aggressive splitting in the file, and I think it is right: they are four different *purchases* — adjacency, monotonicity, a safe greedy order, an event sweep — and the choice of which you are making is what the solution actually is. Merging them would produce one entry saying "sorting helps", which is exactly the useless generality this basis exists to avoid.
- **#13 and #19 kept separate**, which the reverse sweep forced; see below.
- **#16's boundary with inversion counting.** The same-sounding question ("fewest swaps") has two different answers depending on whether swaps are arbitrary or adjacent. Kept as one entry with the distinction stated inline, because the *contrast* is the content and separating them would hide it.
- **#18 (external merge sort) included, despite being a systems question.** It is the only entry whose cost model is I/O rather than comparisons, and it does get asked. Flagged as the likeliest thing to move to a Design basis.
- **#20 (comparison counting) included, despite `O(n)` being unchanged.** Kept precisely because the metric is different: an entry whose whole point is "asymptotics is not what is being asked" earns its place, and "find the second largest efficiently" is a real, common question with a real, non-obvious answer.

**Naming check.** Four retitles. #7 was drafted as "Largest Number", which names a puzzle; it is now *the comparator encodes the objective and reads no field*, which is what a differently-dressed version would share. #11 was drafted as "sort then scan", too vague to navigate to; it is now *sorting makes what you need to compare adjacent*. #14 was drafted as "Meeting Rooms II", which reads like an intervals problem and would have been looked for there; it is now *sort derived events, not the elements*. #19 was drafted as "Queue Reconstruction by Height", pure puzzle-name, and is now *choose the order so later placements cannot invalidate earlier ones*. #10 was checked and kept close to its problem name, since "a string's order is not its meaning's order" is stated in the body and the problem name is the recognisable handle.

**Step 4B — reverse sweep**

Twenty plain-language descriptions navigated against the family headings, in interviewer register and with no mechanism vocabulary. **Two failures, both of which added an axis:**

- **"Put the tallest people first, except each person tells me how many taller people should be ahead of them"** landed nowhere clean. #13 is the closest and is wrong: #13 sorts so that a *scan* can make safe greedy choices, and here nothing is being scanned — you are **inserting into an arrangement that keeps changing**, and the ordering's job is to guarantee that each insertion is invisible to the placements already made. That is a stronger and different requirement. The axis my draft table was missing is *what happens after the sort*: I had listed "a single scan", "two pointers" and "binary search", all of which are **read-only passes**, and had no value for a **mutating insertion process**. That is **#19**, and the axis is now in the table.
- **"Each comparison costs me a phone call, so use as few as possible"** landed nowhere. My cost-model axis had "comparisons cheap" and "key computation expensive", both of which are about *time* — the idea that the **number of comparisons is itself the resource** was absent, and with it the whole tournament family. Every T1 entry silently assumed comparisons are free. That is **#20**, and it is the more interesting of the two findings because it shows the axis table inheriting an assumption from the topic's own folklore: sorting is taught in `O` notation, so the constant-factor questions never get an axis.

Three collisions, all checked and cleared. "Sort by two things at once" reaches #6 and #9, correctly — the comparator and the tuple-key are two implementations of one requirement, and the entries say so. "Beat `n log n`" reaches #3, #4 and ↗ LC 164/347, which is the intended fan-out and exactly the boundary the ↗ row is written to explain. "Sort a linked list" reaches #1 and ↗ LC 148, again the intended pair.

- **4C-i (reciprocity).** Three inbound references pointed at a "Sorting basis" that did not exist — [[Arrays]] ↗ for counting/bucket/radix, and [[Math & Number Theory]]'s exclusion for LC 462. All now resolve here.
- **4C-i produced a false positive, for the second time in two sessions.** I concluded from the inbound reference that *"[[Two Pointers]] #17 owns the partition scheme, so the recurse-into-one-side argument has no owner"* — and it was already written there in full, geometric series included. The probe reads what other files *say about* a target, which systematically understates what the target contains. **The warning in the step is not sufficient, because I wrote the warning and then repeated the error.** Stronger rule: 4C-i's output is a list of *files to open*, never a list of entries to add. - **4C-ii (orphans).** Nothing genuinely homeless. **What I am uncertain about**

- **The Greedy boundary is the fuzziest in this file, and Greedy is unwritten.** #13 is an exchange argument, which is greedy's core content; I kept it because *the sort key is the deliverable* and a reader looking for "which key do I sort by" must find it here. Expect Greedy to want #13, LC 1029, LC 881 and LC 455, and expect this file to keep them cross-listed.
- **The Intervals boundary.** #14 manufactures events from intervals, and Intervals will want it. The cut I intend: **this file owns "the sortable unit is not the input element"; Intervals owns what you do with overlapping ranges.**
- **#18's scope.** If a Design basis appears, external merge sort probably belongs there and should become a ↗ here.
- **Recall is thinnest on comparator *bugs* in languages I use less.** #5's four failure modes are drawn mostly from Java and C++ behaviour. There are probably JavaScript-specific ones worth adding — the default `Array.prototype.sort` comparing as *strings*, so `[10, 9].sort()` gives `[10, 9]`, is a famous one and arguably belongs in #10.
- **Whether T5 is a family or a residue.** Three entries with little in common beyond "the normal cost model does not apply". Kept as a family because the axis (*what the domain allows*, *what the scarce resource is*) is real, but it is the group most likely to be re-cut.

**Completeness confidence: ~88%.** Lower than most files, for two reasons I can name.
