# Agentic Problem to Solution Map

> [!abstract] What this is
> Every recurring problem from the Agentic notes, mapped to its standard solutions, what each costs, and when to pick it. The topic notes explain; this is the index for your head: "I see this symptom, these are my moves, this is the one I'd say first." Same idea as [[25 - Problem to Solution Map]] for classic HLD.

> [!tip] Revision drill
> Cover the options, read only the problem and signal, say the options and the default out loud, then check.

---

## 1. Should This Be an Agent?

### A task is being built as an agent by default

- **Signal:** "build an agent" for a process whose steps are known.

| Option | Costs you | Pick when |
|---|---|---|
| **Single (augmented) call** | Limited to one step | Most tasks; try first |
| **Workflow** (chain, route, parallelise, orchestrator-workers, evaluator-optimizer) | Less flexible | Steps known in advance |
| **Workflow with one agentic step** | Partial unpredictability | One open-ended step inside a known process |
| **Full agent loop** | Variable cost, latency, harder evals | Steps unknowable, feedback available, can be bounded |
| **Multi-agent** | Several times the tokens, compounding errors | Broad parallel work or clearly separate domains |

- **Default:** lowest rung that passes evals. **Depth:** [[01 - Workflows vs Agents]]

### Errors compound across steps

- **Signal:** long trajectories fail often (0.95¹⁰ ≈ 60%, 0.9⁵ ≈ 59%).
- **Moves:** fewer model-decided steps; validation gates between steps; parallel fan-out instead of long hand-off chains; intent-level tools that do several steps in code.
- **Depth:** [[01 - Workflows vs Agents]], [[05 - Multi-Agent Topologies and Concurrency]]

### Picking the loop shape

| Loop | Costs you | Pick when |
|---|---|---|
| **ReAct** | Drifts on long tasks; re-sends history every step | Short, exploratory tasks |
| **Plan-and-Execute** | Bad plan wastes the run; replans add calls | Longer tasks; plan must stay visible |
| **ReWOO** | Can't adapt mid-run | Predictable tool chains; cost/latency matter |
| **Graph / state machine** (LangGraph) | Framework and design work | Need checkpoints, HITL pauses, deterministic nodes |

- **Depth:** [[02 - Execution Loops and Control Topologies]]

### The agent never stops / repeats the same call

- **Moves:** step cap; token and dollar budget per run; wall-clock timeouts; hash `(tool, args)` to catch repeats and return "you already did this"; explicit finish action; escalation path. Enforced by the runtime, never by the prompt.
- **Depth:** [[02 - Execution Loops and Control Topologies]]

### Self-correction makes answers worse

- **Moves:** correct only against external ground truth (tests, compiler, schema validation, `EXPLAIN`, citation checks); cap attempts; Reflexion-style reflections only when a real failure signal exists.
- **Depth:** [[02 - Execution Loops and Control Topologies]]

## 2. Tools and Actions

### The model picks the wrong tool

- **Signal:** dozens of raw endpoints exposed; overlapping descriptions.

| Option | Pick when |
|---|---|
| **Intent-level tools** (`refund_order` instead of five raw calls) | Known procedures, especially side effects |
| **Route first, then expose only that domain's tools** | Clear domains |
| **Tool retrieval** (top-k tools by embedding) | Large tool catalogues |
| **Sub-agent per toolkit** | Many tools in distinct groups |
| **Better names, when/when-not descriptions, enums** | Always |

- **Depth:** [[03 - Tool Engineering and Action Spaces]]

### Tool arguments are invalid or hallucinated

- **Moves:** strict schemas (constrained decoding) for shape; Pydantic validation for semantics; return validation errors as short observations; ask the user when ids can't be resolved; never let the model supply identity.
- **Depth:** [[03 - Tool Engineering and Action Spaces]], [[00 - LLM Fundamentals for Engineers]]

### A tool error kills the whole run

- **Moves:** errors as observations (code, message, hint); runtime retries transient errors itself; raise only for authorisation, budget and policy failures.
- **Depth:** [[03 - Tool Engineering and Action Spaces]]

### A retry or replay duplicates a side effect (double refund)

- **Moves:** idempotency key generated by the orchestrator from run id + step, stored with the result, sent downstream; state-checked downstream operations; human approval for irreversible actions; compensations for multi-step effects.
- **Depth:** [[03 - Tool Engineering and Action Spaces]], [[09 - Durable Execution HITL and Realtime UX]], [[LLD/Foundations/11 - Idempotency and Retries]]

### Many AI clients need the same integrations

| Option | Pick when |
|---|---|
| **MCP server** (tools, resources, prompts over JSON-RPC) | Many hosts/clients consume the same systems |
| **Plain function tools** | One app, a handful of tools |
| **A2A** (agent cards, tasks) | Delegating long jobs to agents owned by other teams/vendors |

- **Watch out:** malicious or over-privileged MCP servers; allow-list, pin, scope tokens. Since the 2026-07-28 spec MCP is stateless (no handshake or session id) and Sampling and Roots are deprecated.
- **Depth:** [[03 - Tool Engineering and Action Spaces]]

### Hundreds of tools fill the context before the request is read

| Option | Pick when |
|---|---|
| **Tool retrieval / `search_tools`** | Large catalogue of independent tools |
| **Code mode** (tools as a code API; the model writes a script, results filtered in a sandbox) | Many tools, big payloads, multi-step data plumbing; you can run a sandbox |
| **Skills** (name and description in context, body loaded on demand) | Repeatable procedures needing long instructions; measure, many skills don't help |

- **Default:** route first, then tool search; code mode when payloads are large. **Depth:** [[03 - Tool Engineering and Action Spaces]]

### Securing a remote MCP server

- **Moves:** server is an OAuth 2.1 resource server; 401 with Protected Resource Metadata; PKCE; `resource` parameter so tokens are audience-bound; validate `iss`; reject and never forward tokens not issued for you; 403 `insufficient_scope` and step-up for more scopes.
- **Depth:** [[03 - Tool Engineering and Action Spaces]]

### An agent acts for a user across several services (whose permissions?)

- **Signal:** a shared API key; the user's long-lived token handed to the agent; a privileged sub-agent acting on a low-privilege request.
- **Moves:** agents as non-human identities with owners and expiry; short-lived task-scoped tokens; token exchange so services see "agent X for user Y"; re-authorise every hop against the originating user (confused deputy, OWASP ASI03); step-up approval for risky actions.
- **Depth:** [[03 - Tool Engineering and Action Spaces]], [[10 - AI Gateway Security and Guardrails]]

### The agent's identity is a static API key

- **Signal:** a long-lived key in an environment variable; nobody knows who owns it; it hasn't rotated in a year.
- **Moves:** attested workload identity per agent (SPIFFE SVID from SPIRE or the cloud platform, minutes-long, auto-rotated); RFC 8693 token exchange for a short-lived, audience-bound token naming user and agent; policy at the tool checks both; audit logs record both.
- **Depth:** [[03 - Tool Engineering and Action Spaces]] → Workload identity

### Agents from other teams or vendors need to cooperate

- **Moves:** A2A (v1.0, March 2026; with MCP under the Agentic AI Foundation since August 2026): Agent Cards, tasks with a lifecycle and streaming; verify **signed Agent Cards**, authenticate both ends, re-authorise against the originating user, treat the remote agent's output as untrusted (OWASP ASI07).
- **Depth:** [[03 - Tool Engineering and Action Spaces]] → A2A

### The agent has to pay for something

| Layer | Option |
|---|---|
| **Checkout** | ACP (OpenAI and Stripe, beta) or UCP (Google) |
| **Proof of what the user approved** | AP2 signed intent and cart mandates |
| **Payment credential** | Scoped single-use token (e.g. Stripe Shared Payment Token), never a card number |
| **Machine payments per call** | x402 |
| **Telling real agents from bots** | Visa Trusted Agent Protocol (signed requests) |

- **Rules:** code enforces limits and merchant allow-lists; fresh approval outside the original intent; idempotent, auditable purchases.
- **Depth:** [[03 - Tool Engineering and Action Spaces]] → Agents That Pay

## 3. Context, State and Memory

### Context keeps growing; agent gets slower, costlier and dumber

- **Signal:** early 15 KB tool payloads still in history at step 12; "lost in the middle".

| Option | Costs you | Pick when |
|---|---|---|
| **Trim tool outputs at the source** | Tool design | Always first |
| **Observation masking** (summarise raw outputs N steps later) | Details need a handle to recover | Tool-heavy runs |
| **Offload to handles + `read(id)` tool** | Extra tool | Big documents, logs, query results |
| **Compaction / summarisation at thresholds** | Extra call; can drop details | Long conversations |
| **Structured state rendered into the prompt** | Schema design | Agents with known sub-goals |
| **Sub-agent isolation** | Extra calls | Messy search-heavy sub-tasks |

- **Depth:** [[04 - State Memory and Context Engineering]]

### Remembering users across sessions

| Tier | Holds | Store |
|---|---|---|
| **Episodic** | Past events | Event log + embeddings |
| **Semantic** | Distilled facts, preferences | Profile store / KG |
| **Procedural** | Learned rules, strategies | Versioned prompt fragments, examples |

- **Write path default:** background consolidation worker, ordered per user; hot-path writes only when needed immediately.
- **Depth:** [[04 - State Memory and Context Engineering]]

### Concurrent sessions overwrite each other's memory

- **Moves:** per-user single-writer queue; compare-and-set with versions; field-level merges; append-only facts resolved at read time.
- **Depth:** [[04 - State Memory and Context Engineering]], [[03 - Concurrency Control]]

### Memory gets poisoned or leaks across users

- **Moves:** persist only validated facts with provenance; hard user/tenant filters before similarity search; TTL and deletion that reaches embeddings; human review for procedural memory.
- **Depth:** [[04 - State Memory and Context Engineering]], [[10 - AI Gateway Security and Guardrails]]

### A task is bigger than one context window (hours or days of work)

- **Signal:** each new session forgets the last; the agent one-shots and runs out of context, or declares victory early.
- **Moves:** an initializer session writes a JSON feature list (all failing), a progress file, an `init.sh` and a first commit; every later session reads them and `git log`, smoke-tests, does one feature, tests it end to end, commits and appends progress. Durable execution handles crashes; this handles context limits.
- **Depth:** [[04 - State Memory and Context Engineering]]

## 4. Multi-Agent

### Choosing a topology

| Topology | Pick when |
|---|---|
| **Router** | Requests fall into clear domains, one specialist each |
| **Supervisor** (hierarchical) | Task needs decomposition and synthesis |
| **Swarm / handoffs** | One specialist at a time owns a conversation |

- **Depth:** [[05 - Multi-Agent Topologies and Concurrency]]

### Sub-agents inherit too much context

- **Moves:** scoped Pydantic task brief in, validated structured result out; never pass the parent transcript; validate at every boundary.
- **Depth:** [[05 - Multi-Agent Topologies and Concurrency]]

### Parallel branches conflict or merge non-deterministically

- **Moves:** explicit reducers (append, union, keyed merge, custom deterministic); sort by stable key before reducing; single-writer fields.
- **Depth:** [[05 - Multi-Agent Topologies and Concurrency]], [[LLD/Concurrency/13 - Designing Thread-Safe Classes]]

### Fan-out trips provider rate limits or blows the budget

- **Moves:** semaphore on concurrent calls; per-branch timeouts and budgets; tolerate partial failure with a threshold; token-aware limits at the gateway.
- **Depth:** [[05 - Multi-Agent Topologies and Concurrency]], [[10 - AI Gateway Security and Guardrails]]

## 5. Retrieval (RAG)

### Answers are wrong even though the document exists

- **Signal:** the fact is in the corpus but never retrieved or retrieved without context.

| Cause | Fix |
|---|---|
| Bad parsing (tables, columns, scans) | Layout-aware parsers, table-to-text, OCR, inspect samples |
| Chunk lacks context | Contextual chunk headers; parent-child retrieval |
| Answer split across chunks | Structure-aware splitting; overlap; return parent section |
| Exact identifiers missed | Hybrid BM25/SPLADE + dense with RRF |
| Right chunk ranked low | Cross-encoder reranking of top 50–100 |
| Conversational follow-up | Query condensation with history |
| Multi-part question | Query decomposition |

- **Depth:** [[06 - RAG Ingestion and Indexing Pipeline]], [[07 - Agentic RAG and Grounding Loops]], [[08 - Vector DB Internals and Hybrid Search]]

### Users see documents they shouldn't

- **Moves:** tenant and ACL metadata on every chunk; filter inside the retrieval query (filter-aware search, never post-filter); per-tenant partitions for large tenants; propagate permission changes as part of freshness.
- **Depth:** [[06 - RAG Ingestion and Indexing Pipeline]], [[08 - Vector DB Internals and Hybrid Search]]

### Small tenants get empty results

- **Signal:** post-filtering global top-k.
- **Moves:** filter-aware single-stage search; brute force over small allowed sets; per-tenant partitions.
- **Depth:** [[08 - Vector DB Internals and Hybrid Search]]

### Stale or deleted documents keep being cited

- **Moves:** content-hash incremental re-ingestion; CDC/webhooks from sources; deletes propagated to every index and cache; doc versions on chunks; TTL metadata.
- **Depth:** [[06 - RAG Ingestion and Indexing Pipeline]]

### Model answers from irrelevant chunks, or loops on missing information

| Option | Pick when |
|---|---|
| **Relevance grading** (small yes/no model, CRAG) | Retrieval is noisy |
| **Capped rewrites (1–2) then deterministic fallback** | Information may be absent |
| **Adaptive retrieval** (skip when not needed) | Mixed chit-chat and knowledge queries |
| **Abstention in the output schema** | Always |

- **Depth:** [[07 - Agentic RAG and Grounding Loops]]

### The question isn't a document question

| Question | Route to |
|---|---|
| Counts, sums, filters over records | Text-to-SQL on a read-only replica with RLS |
| Live state | API tool |
| Recent public info | Web search |
| Multi-hop relationships, corpus-wide themes | GraphRAG / graph queries |

- **Depth:** [[07 - Agentic RAG and Grounding Loops]], [[18 - Knowledge Graphs and GraphRAG]]

### Citations are fabricated

- **Moves:** chunk ids in context; require per-claim citations; verify ids exist, quotes are verbatim, claims are supported (NLI / small judge); regenerate or drop unsupported claims.
- **Depth:** [[07 - Agentic RAG and Grounding Loops]]

### "The context window is huge now; why do we need RAG?"

- **Moves:** usable length is shorter than advertised (RULER), similar distractors hurt (context rot), every token is paid on every call, and a window can't enforce freshness or per-user permissions. Long context wins when the whole relevant source fits; hybrid is retrieve the right documents, then pass them whole.
- **Depth:** [[00 - LLM Fundamentals for Engineers]]

### Retrieval is weak on domain-specific queries

| Option | Pick when |
|---|---|
| Fix hybrid search or chunking | Exact terms or broken chunks cause the misses |
| Fine-tune the reranker | Right documents are in the top 50 but ranked badly; no re-indexing |
| Fine-tune the embedder (in-batch + mined hard negatives) | Recall@50 itself is low; budget a full re-embed |

- **Depth:** [[08 - Vector DB Internals and Hybrid Search]]

### Vector index doesn't fit in memory

| Option | Saves | Costs |
|---|---|---|
| **int8 scalar quantization** | 4× | Small recall loss |
| **Binary quantization + rescoring** | 32× | Needs rescoring |
| **Matryoshka truncation** | 2–6× | Only for Matryoshka-trained models |
| **IVF-PQ** | 30–60×+ | Approximate distances; re-training on drift |
| **DiskANN** | Most RAM | SSD-bound latency |

- **Depth:** [[08 - Vector DB Internals and Hybrid Search]]

### Documents are scans, slides and charts, not clean text

| Option | Costs you | Pick when |
|---|---|---|
| **OCR / layout parser → text RAG** | Charts lost, tables garbled | Text-heavy, exact-quote citations |
| **Vision model on the page** | ~1–1.5k tokens per page per call | Extraction from forms and invoices; questions about a known page |
| **Page-image retrieval (ColPali-style, late interaction)** | ~1k vectors per page; storage and slower search | Decks, reports with charts, scanned manuals |

- **Default:** both views: OCR text for BM25 and citations, page images retrieved and read by a vision model only for the top pages; cite a cropped region, not just a page. Pool and quantise multi-vector indexes and search in two stages.
- **Depth:** [[17 - Multimodal Systems]]

### Images, audio or video blow the token budget

- **Moves:** resize and crop before sending (Claude ≈ width × height / 750 tokens); drop images from context after use; for video (≈ 1M tokens an hour at 1 fps) search the transcript and keyframes first and send only the relevant seconds; for speech, vocabulary hints, read-back of names and numbers, WER per entity type.
- **Depth:** [[17 - Multimodal Systems]]

### Building and keeping a knowledge graph for an LLM

| Option | Pick when |
|---|---|
| **No graph: hybrid vector + BM25 + reranker** | Default; questions are about passages |
| **Graph-seeded hybrid** (vector hits seed a bounded expansion) | Multi-hop questions over known entities |
| **GraphRAG with community summaries** | Corpus-wide themes over a stable corpus |
| **LazyGraphRAG / LightRAG / HippoRAG 2** | Graph benefits with lower indexing cost or frequent updates |
| **Text-to-Cypher** | Precise structured questions over a curated graph |

- **Moves:** fixed schema; extraction with quoted spans checked against the chunk; provenance and ACL on every edge; entity resolution that prefers a missed merge to a wrong one; incremental re-extraction by content hash; summaries per access group; evaluate against a vector baseline by question type.
- **Depth:** [[18 - Knowledge Graphs and GraphRAG]]

### One question must be answered across every document (100k contracts)

- **Moves:** cheap filter with measured recall; one structured map call per document with evidence spans; token-bucket scheduler and batch API; reduce in code; LLM narrative only over the aggregate; progress and partial results.
- **Depth:** [[10 - Batch Document Extraction]] → V4

### Changing the embedding model

- **Moves:** new index; dual-write; backfill; shadow-compare retrieval metrics; switch via alias; keep old index for rollback. Never mix models in one index.
- **Depth:** [[11 - Evals Observability and Silent Drift]], [[06 - RAG Ingestion and Indexing Pipeline]]

## 6. Durability, Humans and UX

### A crash mid-run re-pays for inference and duplicates side effects

| Option | Pick when |
|---|---|
| **Durable execution** (Temporal-style replay of recorded activity results) | Business-critical, long-running, many side effects |
| **Per-node checkpoints** (LangGraph + Postgres/Redis) | Agent-centric apps, pause/resume, inspection |
| **Idempotency keys on side effects** | Always, with either of the above |

- **Depth:** [[09 - Durable Execution HITL and Realtime UX]]

### An action needs human approval

- **Moves:** return 202 + run id; pause durably (interrupt / signal); notify reviewer with the exact action; resume from an authenticated webhook; re-validate state on resume; approval timeouts; audit log.
- **Depth:** [[09 - Durable Execution HITL and Realtime UX]]

### The answer feels slow

| Option | Pick when |
|---|---|
| **Stream tokens + progress events (SSE)** | Default for chat and agent UIs |
| **WebSockets / WebRTC** | Client also streams (voice, cancel mid-stream) |
| **Decouple the run from the connection; resumable event ids** | Mobile or flaky clients |
| **Shorter outputs, fewer sequential steps** | Real latency, not just perceived |

- **Depth:** [[09 - Durable Execution HITL and Realtime UX]], [[12 - LLM Cost and Latency Economics]]

### Voice agent talks over the user

- **Moves:** VAD-triggered barge-in that flushes every audio buffer, cancels LLM generation and TTS, and truncates history to what was spoken; semantic end-of-turn detection; WebRTC transport; streaming at every stage.
- **Depth:** [[09 - Durable Execution HITL and Realtime UX]]

### A run's output can't be tied to the prompt that produced it

- **Signal:** collaborators edit the draft while runs are in flight; "re-run" gives different results and nobody knows why.
- **Moves:** freeze an immutable run snapshot (prompt text, variables, dated model id, parameters, tools) before queueing; runs point only at snapshots; drafts saved with compare-and-swap on a revision; promise same inputs, never same outputs.
- **Depth:** [[13 - Prompt Playground]]

### An agent must act on events and timers, not only on chat

- **Signal:** "follow up if they don't reply in two days"; webhooks from email, CRM or on-call tools; the agent messages too often.
- **Moves:** an event inbox (fast ack, dedupe by source id, batch pending events into one run); timers that write events to the inbox; memory files for what can't be looked up again; a credential proxy and deferred tool calls that end the run and resume from the user's answer; an outbox where "stay quiet" is a normal outcome.
- **Depth:** [[09 - Durable Execution HITL and Realtime UX#Always-On Agents]]

### Users can't tell when the agent is wrong, and give no feedback

- **Moves:** named progress steps; "couldn't find it" as a normal answer; verified inline citations; preview and confirm costly actions; a visible human path; one-click feedback tied to the trace id; treat user edits as labelled corrections.
- **Depth:** [[09 - Durable Execution HITL and Realtime UX#AI UX: What the User Sees]]

## 7. Security and the Gateway

### Provider outage, keys everywhere, no control over spend

- **Move:** an AI gateway owning credentials, routing, retries and fallbacks (evaluated, same tier, residency-aware), hedging for idempotent calls, token-aware limits, budgets, caching, tracing and redaction.
- **Depth:** [[10 - AI Gateway Security and Guardrails]], [[16 - AI Gateway]]

### One tenant's big prompts exhaust the token quota

- **Move:** token bucket in tokens: reserve input + max output before the call, reconcile with actual usage after; per tenant, per user, per feature; global cap under the provider limit; Redis-backed across nodes.
- **Depth:** [[10 - AI Gateway Security and Guardrails]]

### The agent reads untrusted content and could be hijacked (indirect prompt injection)

| Layer | Control |
|---|---|
| **Remove a leg** | No single agent gets private data + untrusted content + an outbound channel |
| **Identity and authorisation** | From the session, checked in services |
| **Least privilege** | Scoped, short-lived credentials per agent/task |
| **Capability separation** | Quarantined model for untrusted text (no tools); privileged planner never sees raw text |
| **Egress control** | Domain allow-lists; strip/proxy links and images in output |
| **HITL** | Approval for high-impact actions |
| **Classifiers and prompt hygiene** | Probabilistic extra layer, never the boundary |

- **Depth:** [[10 - AI Gateway Security and Guardrails]]

### Running model-generated code

| Option | Pick when |
|---|---|
| **gVisor** | Multi-tenant execution on Kubernetes |
| **Firecracker microVM** | Untrusted code at scale, strongest isolation |
| **Managed sandbox** (E2B-style) | Need an interpreter without running isolation infra |
| ~~Plain container~~ | Trusted code only |

- **Policy:** no network (or allow-list), no secrets, resource and time limits, ephemeral, output treated as untrusted.
- **Depth:** [[10 - AI Gateway Security and Guardrails]]

### PII flowing to providers and logs

- **Moves:** redaction/tokenisation before external calls; provider retention and zero-data-retention terms; data-residency routing; retention and access control on traces; deletion that reaches logs, caches, embeddings, memories.
- **Depth:** [[10 - AI Gateway Security and Guardrails]], [[18 - Security]]

### "How would you threat-model this agent?"

- **Move:** list every tool, credential, memory store and peer agent; ask which of OWASP's agentic risks (ASI01 goal hijack … ASI10 rogue agents) reaches each; apply **Least Agency** first (remove autonomy and permissions), then controls; **Strong Observability** for the rest.
- **Depth:** [[10 - AI Gateway Security and Guardrails]]

### "How do you know the defences actually hold?"

- **Move:** a red-team pipeline: threat model → attack corpus per category (jailbreak, indirect injection in documents, tool results and images, exfiltration, privilege abuse, tool misuse, over-refusal probes) → automated multi-turn variants (Promptfoo, garak, PyRIT) → attack the full agent with tools in a sandbox → score on **tool calls from the trace**, not the judge's verdict → humans confirm → attack success rate per category at a stated number of attempts → fix by removing agency first → every finding becomes a CI regression case.
- **Depth:** [[10 - AI Gateway Security and Guardrails]] → Red-Teaming

### "What about regulation?"

- **Move:** name the regime and its effect on the design: DPDP (consent, purpose, erasure through transcripts, memories and embeddings); EU AI Act after the Digital Omnibus: transparency (AI disclosure, labelled and machine-marked generated content) since 2 August 2026, high-risk duties (hiring, credit, education) from 2 December 2027; classify the use case and keep audit logs and human oversight.
- **Depth:** [[10 - AI Gateway Security and Guardrails]] → Regulation

### The system you need has no API (portal, partner dashboard, desktop app)

| Option | Pick when |
|---|---|
| **Scripted automation** (Playwright, RPA) | Stable pages, fixed steps |
| **Browser agent** (DOM + screenshot, semantic targets) | Varied tasks on web apps |
| **Computer-use agent** (screenshots, whole desktop) | No DOM: desktop apps, canvases |

- **Moves:** isolated browser per task from a worker pool; verify the postcondition against backend truth, read before any retry; credentials injected by the harness; MFA hands off to a human; domain allow-list; approval for money and sends.
- **Depth:** [[16 - Computer Use and Browser Agents]]

## 8. Quality, Evals and Drift

### "How do you know it works?"

| Tier | Checks | When |
|---|---|---|
| **Deterministic** | Schema, router label, tool and args, limits | Every commit |
| **Trajectory** | Right tools, order, no forbidden actions, step budget | Agent changes; sampled prod |
| **Outcome** | Real environment state, reference answers, RAG faithfulness | Releases, nightly, sampled prod |

- **Depth:** [[11 - Evals Observability and Silent Drift]]

### The LLM judge can't be trusted

- **Moves:** binary specific rubrics; reference answers or source context; evaluate both orders (position bias); different model family (self-preference); length control (verbosity); calibrate against 100–200 human labels.
- **Depth:** [[11 - Evals Observability and Silent Drift]]

### Eval scores can't be trusted, or stopped moving

- **Moves:** capability suite (starts low) plus regression suite (~100%), tasks graduate between them; add harder tasks when a suite saturates; unambiguous tasks with a reference solution each; balanced should/shouldn't cases; grade outcomes not exact paths, with partial credit; one judge per dimension with an "Unknown" option; isolated trials; read transcripts. A 0% task is usually a broken task or grader.
- **Depth:** [[11 - Evals Observability and Silent Drift]]

### "Model B beat model A by 1.5 points. Is that real?"

- **Moves:** report a standard error with every score; compare **paired differences** on the same questions (frontier models' per-question scores correlate 0.3–0.7, so paired SEs are much smaller); **cluster** the SE when questions share a passage, repo or template (can be 3× the naive SE); resample each question k times with chain of thought; Wilson intervals for small n or rates near 100%; size the eval with power analysis (about 1,400 paired questions to see 3 points at 80%); correct across many evals (Holm, Benjamini-Hochberg); bootstrap statistics with no formula.
- **Depth:** [[11 - Evals Observability and Silent Drift#Eval Statistics: Error Bars on Every Score]]

### Spotting hallucinations with no reference answer

| Signal | Pick when |
|---|---|
| **Token log-probabilities** | Cheap first filter on short factual answers; logprobs available |
| **Self-consistency / SelfCheckGPT** | Black-box API; offline audit of sampled traffic |
| **Semantic entropy** (cluster samples by meaning) | Strongest unsupervised signal for factual Q&A; worth N× generation |
| **Probes on hidden states** | Self-hosted open weights at volume |
| **Verify claims with tools** | High-stakes answers; agent claims about state |

- **Caveat:** these detect uncertainty; confident errors pass. Ground with retrieval first.
- **Depth:** [[11 - Evals Observability and Silent Drift#Hallucination Detection Without a Reference]]

### Nothing is down, but the answers got worse (AI on-call)

- **Moves:** a **quality SLO** (share of sampled responses passing graders, 28-day budget, burn-rate alerts); page on spend rate, steps per task, guardrail spikes and provider errors; **mitigate first** (config rollback, fallback model, kill switch, human review, spend cap), then diff failing vs passing traces by prompt, model, index and tool version; check input-mix shift and silent provider updates; size the blast radius in wrong **actions**; failing cases join the regression suite. Never let the model be the only reporter of a tool failure (it narrates errors as success).
- **Depth:** [[11 - Evals Observability and Silent Drift#Quality SLOs and Incident Response]]

### Rolling out a prompt or model change safely

- **Moves:** prompts in git with a `prompt_version` on every trace; pinned model versions; offline evals gate the merge; shadow → canary (1–5%) → A/B or ramp; rollback is a config flip; watch success per intent, refusals, cost and steps per task.
- **Depth:** [[11 - Evals Observability and Silent Drift]], [[13 - GPU Serving and Disaggregated KV Cache]] (model registry)

### "Is this good enough to launch?"

| Layer | Examples |
|---|---|
| **Business** | Resolved cases, conversion, cost per resolved case |
| **User** | Task completion, draft acceptance, edit distance, repeat contact, escalations |
| **Task quality** | Offline evals: groundedness, correctness, tool-call correctness |
| **System** | p95 latency, availability, cost per **successful** task |
| **Risk** | Unsafe output, leakage, harmful actions, **over-refusal**, segment gaps |

- **Moves:** hard guardrails separate from goal metrics, never blended; randomise by user or conversation (tenant or switchback for B2B); watch novelty effects; shadow or staged rollout when A/B isn't possible; write the ship rule before the test.
- **Depth:** [[11 - Evals Observability and Silent Drift]] → Product Metrics

### "How does the system get better after launch?"

- **Move:** the data flywheel: traces plus implicit signals (edits, rephrasing, escalations) → mine and cluster failures → label (humans + calibrated judge) → feed both eval sets and training data → cheapest fix first (prompt, retrieval, routing, then fine-tune or distil) → same eval and canary gate. Keep eval and training data separate; train only on verified outputs.
- **Depth:** [[15 - Post-Training and Model Adaptation]]

### Evaluating a conversational agent that changes state (support, booking)

- **Moves:** τ-bench method: a simulated user with a private goal and persona, the agent's real tools on a sandbox DB, a written policy, and grading on the **final database state** against a goal state; repeat each task k times and report **pass^k** (all k succeed), not pass@k; split tasks into always-pass, always-fail (usually a tool or policy gap) and flaky; calibrate the simulator against real conversations.
- **Depth:** [[11 - Evals Observability and Silent Drift]]

### System returns 200 OK but is wrong or looping

- **Moves:** alert on task success, cost per task, steps per task, tool error rate, abstention and truncation rates; semantic circuit breakers to a fallback; pinned model versions; contract tests on tools.
- **Depth:** [[11 - Evals Observability and Silent Drift]]

### Semantic cache returns the wrong answer

- **Moves:** never semantically cache actions or transactions; exact-match caching for deterministic calls; scope keys by tenant/user/locale/data version; entity checks plus high thresholds; TTLs; measure false-hit rate.
- **Depth:** [[11 - Evals Observability and Silent Drift]]

### Where did this bad answer come from?

- **Move:** one trace per run, one span per LLM/tool/retrieval step with model, tokens, cost, prompt version, chunk ids, finish reason (OpenTelemetry GenAI conventions); every incident becomes an eval case.
- **Depth:** [[11 - Evals Observability and Silent Drift]]

## 9. Cost and Latency

### Cost per task is too high

| Lever | Pick when |
|---|---|
| **Prompt caching** (stable prefix first, variable last) | Long system prompts, tools, reference docs, multi-turn agents |
| **Context compaction** | Agent input growing quadratically with steps |
| **Routing / cascades** | Most traffic is easy |
| **Batch API** | Offline work (evals, backfills, enrichment) |
| **Fewer steps / intent tools / workflows** | Agents with predictable procedures |
| **Shorter outputs, reasoning-effort control** | Output and reasoning tokens dominate |
| **Distil to a small model** | Narrow, high-volume task |

- **Depth:** [[12 - LLM Cost and Latency Economics]]

### Prompt caching isn't hitting

- **Signal:** timestamps, user names or request ids at the top; tools reordered; history rewritten every turn.
- **Moves:** stable content first; round dates; fixed tool order; compact in chunks at thresholds; prefix-aware routing when self-hosting.
- **Depth:** [[12 - LLM Cost and Latency Economics]], [[13 - GPU Serving and Disaggregated KV Cache]]

### API or self-host?

| Option | Pick when |
|---|---|
| **API** | Variable/modest volume, need frontier quality, small team |
| **Self-host** | High sustained utilisation, residency/privacy, custom or fine-tuned models |
| **Hybrid** | Frontier API for hard steps, self-hosted small models for volume |

- **Depth:** [[12 - LLM Cost and Latency Economics]], [[14 - Quantization Decoding and VRAM Math]]

### Does the feature make money? (pricing and margin)

| Pricing | Pick when |
|---|---|
| **Per seat** | Usage per user is predictable; add fair-use caps for power users |
| **Per token or call** | Developer platforms; customers accept a variable bill |
| **Per outcome** | The outcome is countable and agreed (resolution, saved cancellation); you can carry failed attempts |

- **Moves:** cost per resolution = cost per conversation / resolution rate; gross margin against price; look at the cost distribution per user, not the mean; check what doubling usage does under each model.
- **Depth:** [[12 - LLM Cost and Latency Economics#Unit economics and pricing]]

## 10. Serving Infrastructure

### Concurrency is limited / requests OOM on long contexts

- **Signal:** KV cache (~0.3 MB/token for a 70B GQA model) fills GPU memory; preemptions.

| Option | Effect |
|---|---|
| **PagedAttention** (vLLM) | Removes KV fragmentation; more sequences fit |
| **FP8 / INT8 KV cache** | ~2× tokens in flight |
| **GQA / MQA / latent-attention models** | Smaller KV per token |
| **Tiered / offloaded KV** (CPU, SSD, remote via LMCache/Mooncake) | Keep reusable prefixes without HBM |
| **Admission control, max context limits** | Stop over-admission |
| **More GPUs / tensor parallel** | More memory per replica |

- **Depth:** [[13 - GPU Serving and Disaggregated KV Cache]], [[14 - Quantization Decoding and VRAM Math]]

### Token streams stutter when long prompts arrive

| Option | Pick when |
|---|---|
| **Continuous batching** | Always (baseline) |
| **Chunked prefill** | Mixed long-prompt and streaming traffic |
| **Disaggregated prefill/decode pools + KV transfer over RDMA** | Large scale, strict TTFT and ITL SLOs, prefill-heavy workloads |

- **Depth:** [[13 - GPU Serving and Disaggregated KV Cache]]

### Agent steps re-prefill the whole history every call

- **Signal:** round-robin load balancing across GPU nodes.
- **Moves:** prefix caching (RadixAttention / automatic prefix caching); prefix-aware routing scored by cache hit minus load; session stickiness; distributed KV cache to fetch instead of recompute.
- **Depth:** [[13 - GPU Serving and Disaggregated KV Cache]]

### Model doesn't fit, or decode is too slow

| Option | Costs you | Pick when |
|---|---|---|
| **FP8 weights + activations** | Needs supported hardware | High-throughput serving |
| **INT4 weight-only (AWQ/GPTQ)** | Reasoning quality loss | Memory-bound; simple, high-volume steps |
| **Speculative decoding** (EAGLE, draft model, n-gram) | Draft overhead; less gain at high batch | Latency-sensitive, lower batch |
| **Tensor / pipeline / expert parallelism** | Interconnect requirements | Model bigger than one GPU |

- **Rule:** keep planners and reasoners at FP8/BF16; evaluate quantized models on your trajectories.
- **Depth:** [[14 - Quantization Decoding and VRAM Math]]

### Structured output inflates time to first token

- **Moves:** pre-compile and cache grammars for static schemas (XGrammar-style engines); small, reused schemas; reasoning fields before answer fields.
- **Depth:** [[14 - Quantization Decoding and VRAM Math]]

### Sizing a deployment

- **Formula:** VRAM ≈ weights (params × bytes) + KV (per-token bytes × tokens in flight) + ~10–20% overhead; cost per 1M tokens ≈ GPU $/hour × GPUs ÷ (aggregate tokens/s × utilisation × 3600 ÷ 10⁶).
- **Depth:** [[14 - Quantization Decoding and VRAM Math]]

### "Is this compute-bound or memory-bound? How fast can it go?"

- **Method:** FLOPs (`2·m·k·n` per matmul, ~2 × params per token) ÷ bytes moved = arithmetic intensity; compare with the ridge point (H100 ≈ 295 FLOP/byte). Below → time ≈ bytes ÷ bandwidth; above → FLOPs ÷ peak. Weight-matmul intensity ≈ tokens per step, so decode under ~300 tokens is memory-bound.
- **Sharding:** contracting dimension unsplit → no comms; one input split on it → AllGather; both split → local matmul + AllReduce (2× AllGather). Megatron TP = two activation all-reduces per layer; keep TP inside NVLink, pipeline or data parallel across nodes.
- **Depth:** [[14 - Quantization Decoding and VRAM Math#Roofline and Sharding Arithmetic]]

### Shipping a new model version to thousands of GPU hosts

- **Signal:** model size × fleet size is a petabyte per release; the origin would need hours.
- **Bound first:** time ≥ max(F ÷ seed upload, F ÷ slowest download, N·F ÷ total upload) ≈ F ÷ node link with a swarm; twice that if upload and download share one link.
- **Moves:** chunked, content-addressed, signed artifacts in a rack-aware swarm with regional seeds; a control plane of per-cohort assignments with a generation that only grows; fetch early, activate later in drained batches; previous version kept warm; GPU-to-GPU loading from serving peers; quality gates per rollout stage with auto-pause.
- **Depth:** [[14 - Model Weight Distribution to a GPU Fleet]], [[13 - GPU Serving and Disaggregated KV Cache]]

### Minute-long GPU jobs (video, image generation) and demand far above capacity

- **Signal:** one job holds a GPU for minutes; peak submissions are 10× what the fleet can run; one heavy user takes the fleet.
- **Moves:** submit returns a job id; every state change is a conditional update with attempt and fencing epoch; leases, heartbeats, reaper and reconciler; checkpoints for long jobs; weighted fair queueing on **GPU-seconds**, charged by estimate and corrected at completion; bounded tier queues with ETAs and 429s; whole-node reservations and backfill for multi-GPU jobs.
- **Depth:** [[15 - GPU Job Scheduler for Video Generation]]

### GPUs sit idle or jobs never start on a shared cluster

- **Signal:** a 16-GPU job holds 12 GPUs and waits; free GPUs are scattered one per node; a bad GPU keeps failing jobs.
- **Moves:** gang scheduling (Kueue, Volcano, Slurm); best-fit placement and a fragmentation metric; topology-aware placement on NVLink islands and leaf switches; DCGM and Xid monitoring with rate-limited cordon and drain; MIG for isolated small tenants.
- **Depth:** [[19 - GPU Cluster Infrastructure and Operations]]

### A model is too big to train, or the run is slow

- **Moves:** count 16 bytes per parameter for mixed-precision Adam; FSDP/ZeRO to shard state; TP inside the node, PP across nodes (bubble ≈ (p − 1)/(m + p − 1)), EP with all-to-all for MoE; FlashAttention and context parallelism for long sequences; activation checkpointing; asynchronous RL with bounded staleness for post-training.
- **Depth:** [[20 - Training and RL Systems at Architect Depth]]

## 11. Adapting the Model

### Prompting isn't enough

| Need | Move |
|---|---|
| Changing or private **facts** | RAG, not fine-tuning |
| Reliable **format, style, domain behaviour** | SFT / LoRA |
| **Cheaper** narrow high-volume task | Distil into a small model |
| Better **tool-use decisions** in your environment | SFT on verified trajectories, then RLVR |
| Better **reasoning** on checkable tasks | RLVR (GRPO) or more test-time compute |
| **Tone / preference** alignment | DPO |

- **Depth:** [[15 - Post-Training and Model Adaptation]]

### Hand-tuned prompts plateau or break when the model changes

| Option | Pick when |
|---|---|
| **BootstrapFewShot** (DSPy) | Small labelled set, quick win |
| **MIPROv2** | Tens to hundreds of examples, several modules |
| **GEPA** (reflective prompt evolution) | Rich textual feedback (judge rationales, test output); agents and multi-step pipelines |

- **Moves:** needs a metric and a labelled set first; hold out a test split; version optimised prompts and ship through the normal eval and canary gate; fine-tune only if a smaller model or frozen behaviour is needed.
- **Depth:** [[15 - Post-Training and Model Adaptation]] → Automatic Prompt Optimisation

### Fine-tuned model copies the teacher's bad habits

- **Moves:** keep only outcome-verified, minimal-step, policy-clean trajectories (rejection sampling); evaluate on held-out tasks vs teacher; optional RLVR after SFT.
- **Depth:** [[15 - Post-Training and Model Adaptation]]

### RL training "succeeds" but the model got worse

- **Signal:** reward hacking: passes the verifier without solving the task.
- **Moves:** robust verifiers, held-out tests, length penalties, KL constraints, trajectory review.
- **Depth:** [[15 - Post-Training and Model Adaptation]]

### Many per-tenant or per-task fine-tunes to serve

- **Moves:** LoRA adapters on one shared base; multi-LoRA serving (S-LoRA paged adapter memory, Punica SGMV kernels); adapter registry and retraining plan on base upgrades.
- **Depth:** [[15 - Post-Training and Model Adaptation]]
